# 首次编译检查清单

> 全部 WPF 代码（`Pulpit.App`，约 3100 行 C# + 510 行 XAML）**从未经过编译器**——
> 开发在 macOS 上进行，而 WPF 在 macOS 上连编译都不支持。
>
> 本清单是一次逐文件静态审查的产物：把「我不确定的外部 API」按可疑度排序，
> 每条给出**位置**、**不确定什么**、以及**万一报错怎么改**。
> 首次 `dotnet build` 报错时照单查，比从头读堆栈快。
>
> 审查日期 2026-08-20。已在审查中修掉 3 处（见文末「审查中已修」）。

---

## 怎么用

```powershell
dotnet build Pulpit.sln -c Debug 2>&1 | Select-String -Pattern "error"
```

先跑 Core（它在任何平台都能编译，先把它排除掉）：

```powershell
dotnet build src\Pulpit.Core\Pulpit.Core.csproj
dotnet test  tests\Pulpit.Core.Tests            # 153 个测试方法 / 158 条数据行
```

`Pulpit.Core` 过了，说明剩下的错全在 App 层，范围立刻缩小到本清单。

## 一级：最可能报错（置信度 < 90%）

### ① `TextCompositionManager` 的三个路由事件字段

**位置**：`src/Pulpit.App/Views/ControlWindow.xaml.cs` `AttachImeTracking()`（约 160/164/168 行）

```csharp
InputBox.AddHandler(TextCompositionManager.TextInputStartEvent,  new TextCompositionEventHandler(OnCompositionStart));
InputBox.AddHandler(TextCompositionManager.TextInputUpdateEvent, new TextCompositionEventHandler(OnCompositionUpdate));
InputBox.AddHandler(TextCompositionManager.TextInputEvent,       new TextCompositionEventHandler(OnCompositionEnd));
```

**不确定什么**：这三个 `public static readonly RoutedEvent` 字段的确切名字与可见性。

**万一报错怎么改**（按优先级）：

1. 换成同类的静态注册方法（同一套 API 的另一种写法）：
   ```csharp
   TextCompositionManager.AddTextInputStartHandler(InputBox, OnCompositionStart);
   TextCompositionManager.AddTextInputUpdateHandler(InputBox, OnCompositionUpdate);
   TextCompositionManager.AddTextInputHandler(InputBox, OnCompositionEnd);
   ```
2. 退到 `UIElement` 上一定存在的事件（能力略弱，但够用）：
   ```csharp
   InputBox.PreviewTextInput += (_, _) => SetComposing(true);
   InputBox.TextInput        += (_, _) => SetComposing(false);
   ```
3. 最坏情况：整块删掉，`IsComposing` 恒为 false。

**删掉的后果要看清**：M3 验收第一条（用微软拼音打「神爱世人」，全程按 Enter 选词，
副屏无变化）**仍然通过**——那条靠的是 `AcceptsReturn=False` + 全窗口无 `IsDefault` 按钮，
与组合态跟踪无关。丢掉的只是「F9 在输入法组合中到达时拒绝送出」这层额外保护。
**不要因为这块报错就去给按钮加 `IsDefault`**，那会直接违反 L8。

### ② `HwndSource` 的 7 参构造

**位置**：`src/Pulpit.App/Interop/GlobalHotkey.cs` `EnsureSink()`（约 178 行）

```csharp
_source = new HwndSource(0, 0, NativeMethods.WS_EX_TOOLWINDOW, 0, 0, "PulpitHotkeySink", IntPtr.Zero);
```

**不确定什么**：参数个数与顺序（`classStyle, style, exStyle, x, y, name, parent`）。
审查中已从命名实参改为位置实参——形参名不值得赌。

**万一报错怎么改**：
```csharp
var p = new HwndSourceParameters("PulpitHotkeySink") { Width = 0, Height = 0 };
_source = new HwndSource(p);
```
（丢掉 `WS_EX_TOOLWINDOW`，代价是这个 0×0 隐藏窗口理论上可能进 Alt+Tab。
它没有 `WS_VISIBLE`，实际不会出现，但 M0 验收第 5 项要人工确认一下。）

### ③ `FormattedText` 的可写属性

**位置**：`src/Pulpit.App/Views/OverlayWindow.xaml.cs` `MeasureBodyHeight()`（约 333 行）

```csharp
new FormattedText(text, culture, flow, typeface, fontSize, brush, pixelsPerDip)
{
    MaxTextWidth = maxWidth,
    LineHeight   = lineHeight,
    Trimming     = TextTrimming.None,
    TextAlignment = TextAlignment.Center,
}
```

**不确定什么**：这四个属性是否都可写。`MaxTextWidth` 与 `Trimming` 基本确定，
`LineHeight` 与 `TextAlignment` 略低。

**万一报错怎么改**：把报错那个属性从初始化器里删掉即可，**但要知道代价**：
删掉 `LineHeight` 后，测量用的行高变成字体自然行高，而呈现侧
（`BodyText.LineHeight = size × 1.35`）仍是 1.35 倍——两边不一致，字号会算偏，
长节可能溢出一行。若必须删，请同时把 `OverlayWindow.SetFontSizes` 里的
`BodyText.LineHeight` 赋值也删掉，让两边都用自然行高。**这两处必须同时改。**

## 四级：编译能过，但**行为**未经任何验证

这一级不是编译问题，是首次运行时要盯的地方。按后果排序：

1. **`FormattedText` 与 `TextBlock` 的行高模型是否严丝合缝**
   两边共用 `OverlayTheme.LineHeightFactor = 1.35` + `LineStackingStrategy=BlockLineHeight`
   强行对齐。若差几像素，最长节（申 30:9-10，106 字）可能溢出一行。
   **怎么看**：投「申30:9」，看正文有没有被 `ClipToBounds` 裁掉尾部。

2. **`VisualBrush` 镜像一个 `AllowsTransparency` 窗口**
   `ControlWindow.AttachPreview()`。若预览区一片空白或闪烁，退路是手写一个副本
   （代价：以后改了正文排版规则容易忘了同步改预览）。

3. **单文件发布时 `e_sqlite3.dll` 能否自解压**
   `publish.cmd` 已带 `IncludeNativeLibrariesForSelfExtract=true`。
   若报找不到原生库，去掉 `PublishSingleFile` 改成普通目录发布。

4. **两个置顶窗口各带 2 秒心跳**
   正文在底部三分之一、角标默认右上角，空间上不重叠，理论上不争 Z 序。
   若观察到闪烁，把两个心跳错开（`OverlayWindowStyler` 的 `HeartbeatInterval` 加个偏移）。

5. **IME 组合态事件是否真的按预期触发**
   必须用真实的微软拼音验。见一级 ①。

## 审查中已修

| 位置 | 问题 | 处理 |
|---|---|---|
| `GlobalHotkey.EnsureSink` | 对 `HwndSource` 7 参构造用了**命名实参**——形参名写错就编译不过，而这个赌注零收益 | 改为位置实参 + 行尾注释标注每个参数 |
| `SingleInstanceGuard.TryAcquire` | 同上，`new Mutex(initiallyOwned: true, …)` | 改为位置实参 |
| `BadgeWindow.Fade` | 判断是否直切用 `_theme.FadeMs`，时长却用写死的 `200ms`——两个来源，`fadeMs` 调成 300 时角标仍 200ms | 时长改用同一个 `_theme.FadeMs` |

## 审查中确认无误

- 三个窗口的构造顺序：碰控件的语句全部在 `InitializeComponent()` 之后
- XAML 事件处理器 28 个、`x:Name` 54 个，与 code-behind 双向核对无悬空、无签名不匹配
- `x:Class` 与 code-behind 的 `namespace` + `partial class` 三窗口全部一致
- 花/圆/方括号全部配平（已剔除字符串与注释）
- 无重复成员名、无真死代码（`On*` 处理器全部经 XAML 或 `+=` 或 `AddHandler` 接线）
- `Pulpit.Core.Content.Page` 与 `System.Windows.Controls.Page` 同名：只有 `OverlayWindow`
  用到 `Page`，而它**没有**引入 `System.Windows.Controls` —— 无二义性
- 外部 API 的命名实参只剩 `File.Move(…, overwrite:)` 与 `Directory.Delete(…, recursive:)`，
  两个签名在 .NET 里非常稳定
- 外观面板的初始化重入已被 `_loadingAppearance` 闸门挡住：给 Slider / ComboBox / TextBox
  赋值会触发各自的 changed 事件，没有闸门的话窗口一打开就会被当成「操作员改了外观」
